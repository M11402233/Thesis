## 一、討論事項

### 1. 主動探測（challenge-response）
- 老師建議以「先假設節點為壞」為出發點：(1) 先證明好節點能通過；(2) 對節點下一個「挑戰」（例如改變資源或觸發 handoff），檢查其行為是否隨挑戰而變化，以確認其仍在控制範圍內。
- 老師指出 token 無法驗證被攻陷節點，因其 token 仍為合法（與本研究「OAuth 擋不住主要威脅」之立場一致）。
- 老師認為 RQ4 及新增之招數「也不賴」。【待確認：「新增這個招數」所指為何】

### 2. 重放攻擊
- 老師提問：攻擊者隔天重送前一天的結果、連送數日仍未被抓到時，P1／P2 是否能抓到重複出現之情形。
- 記錄者註：S_i 以同窗 peer 為參照，重放之舊值原則上與當窗不符，但目前**無實驗證據**，不得於正文宣稱。

### 3. 賽局與收斂
- 研究生說明：偵測端與攻擊端各自學習，擬設停止條件並以分析方法判斷結果。老師表示若分析可行，可發表為相當不錯之論文。
- 研究生表示 W*（雙方互相學習後的理想情況）為尚未驗證之假設，擬先完成實驗，因加入後 performance 可能反而變差。
- 老師就「是否列為第二篇」的前提表示：P1–P3 三個流程之內容須先足夠成篇。【待確認：老師對拆篇之最終意見】

### 4. 論文深度
- 老師提醒審稿者（含 Jodie 老師）可能認為內容粗淺：各分項（UE 數量變化、peer 數、移動軌跡）皆有他篇研究。
- 研究生回應：各分項可在文獻中找到，新的是組合並量測 PRB 資源；並以加入對抗式學習補足深度。
- 研究生計畫於修改完老師提及之項目後，先寄一版給 Jodie 老師。實驗預計兩週可完成第一輪。【待確認：「第一轉」之範圍】

### 5. 量測口徑
- 研究生提出量測 CPU 使用量，以及深度學習與驗證共用同一顆 CPU 時是否互相拖累。
- 老師指出：應量 **service time**（請求進入機器處理完畢離開之時間），不是 CPU 使用率；共用 CPU 會使環境不單純、審稿者無法判斷各部分貢獻。
- 做法：驗證與深度學習**分開量測**（前人做法為分兩台機器量），再相加，以求公平。PRB 僅反映使用率，service time 仍須量。

### 6. 資源與行政
- 實驗室機器緊（多人每人使用三、四台）；老師請研究生向同學詢問尚有幾台可用。
- 邀請 Jodie 老師擔任共同指導：研究生同意，老師表示邀請亦可由老師發出。
- 後續延伸：將架構延伸到核心網路（零信任）、納入 AI、一系列 trust 主題；並提到歐盟計畫之構想。【待確認：細節與時程】
