## 0. 一句話

偵測端與攻擊端改成兩個互相對抗的學習模型：被入侵的 DU 學習怎麼慢慢改變上報而不被抓，偵測端學習怎麼判斷 DU 是否被入侵。同時在 DU 與 CU／RIC 之間加上 OAuth 2.0 式的零信任授權。**C_i 與 H_i-D2 保留為規則式硬否決；DRL 取代的是 S_i 與 H_i-D1 那一層（L2）的決策。**

## 3. 架構修正（重點：DU–CU 之間）

### 3.1 修正後的整體結構

```
             ┌────────────── Authorization Server（OAuth 2.0, RFC 6749）──────────────┐
             │ 發 access token；scope = 該 DU 可上報的 cell ID、量測類型、可發出的請求種類 │
             └────────────▲─────────────────────────────────────────┬──────────────┘
                token 申請 │                                         │ token 驗證
                           │                                         ▼
 ┌───────────────┐ 每筆上報／請求附 token ┌──────────── Near-RT RIC（或 CU，見 P2）─────────────┐
 │ O-DU（誠實）   │ ────────────────────▶ │ ⓪ AuthZ Gate：驗 token 與 scope → 不符即 R1_AUTHZ   │
 ├───────────────┤                       │ ① Detection xApp：C_i／S_i／H_i 證據（不變）          │
 │ O-DU（被入侵） │ ────────────────────▶ │ ② Trust Assessment xApp：                            │
 │ 學習型攻擊者   │ ◀── 判定結果（回饋）── │     L1 規則：R1_STAGE1、R1_AUTHZ、C_i、H_i-D2         │
 └───────────────┘                       │     L2 DRL policy：讀 S_i、H_i-D1 證據與歷史            │
                                         │     L3 規則：證據不可得 → abstain                       │
                                         │ ③ Policy Enforcement xApp：allow/restrict/exclude/defer │
                                         │ ④ Available-resource evaluation xApp（不變）            │
                                         └──────────────────────────────────────────────────┘
```

### 3.2 OAuth 2.0 零信任層的設計

| 元件 | 內容 |
|---|---|
| 授權伺服器 | 依 RFC 6749 發 access token；token 含 DU 身分、scope、到期時間 |
| scope（最小權限） | 該 DU 只能上報自己負責的 cell ID、被允許的量測類型、被允許的請求種類（例如不得替其他 cell 宣告負載） |
| 檢查點 | ⓪ AuthZ Gate，位於 Detection 之前；**每一筆上報、每一個請求都檢查**（教授：每個請求都要個別檢查） |
| 規則 | **新增 `R1_AUTHZ`**（token 無效、過期或 scope 不符 → rejected）。**保留 `R1_STAGE1`** 表示身分前提（IKEv2／IPsec），兩者語意不同：前者是「能不能做」，後者是「是不是你」 |
| token 生命週期 | 短效 token；依信任狀態縮小 scope 或停止續發屬選配，**P1、P2 定案後再做** |

### 3.3 OAuth 與三類證據的分工（論文必須寫清楚）

| 層 | 回答的問題 | 擋得住 | 擋不住 |
|---|---|---|---|
| OAuth 授權層 | 這個 DU **能不能**報這個東西、提出這個請求？ | 未登記或已撤銷的 DU；替**不屬於自己的 cell ID** 上報或提出請求（與 E2 Setup 之 cell 清單部分重疊）；超出最小權限的請求種類 | 〔11-07 修正〕**本論文的主要威脅**：被攻陷的 DU 持有合法 token，在 scope 內竄改自己 cell 的數值。scope 限制 cell ID，不限制 UE ID（UE 會移動），故**擋不住**「把別 cell 的 UE 報成自己的」（搬移攻擊） |
| C_i／S_i／H_i + DRL | 它報的數值**是不是真的**？ | 數值、成員、移動的不一致 | 落在偵測能力以下的偏移（Q4 已量化規則版的上界） |

〔11-07 修正〕一句話定位：**OAuth 限制 DU 能要求什麼；一致性檢查質疑它說了什麼。** 依逐字稿，教授強調的是最小權限（"he can change only what needs to change, nothing more"）與逐請求檢查，以降低被攻陷節點的影響範圍，而不是靠 OAuth 驗證數值。

教授原話可作為動機：零信任無法完全阻止內部攻擊（DU 宣稱自己空閒、要求把使用者都轉給它卻不服務），目標是把影響降到最低。

**引用注意**：RFC 6749 為 IETF 標準。O-RAN 文件中 OAuth 2.0 的已核實出處只有 xApp-TR §6.5（Solution #4，xApp 存取 Near-RT RIC API）與 SRCS §5.1.3。**不得宣稱 O-RAN 規範要求在 E2 或 F1 上使用 OAuth。** 加入此層的理由是 ZTA-TR §7.3.4 NOTE 3：E2 上認證即授權，SCTP 沒有原生授權方法。Hashem Eiza et al. (2025) 的 PDP／PEP 逐 session 授權是最接近的相關工作，需在相關研究中區分。

### 3.4 CU 與 RIC 的對應（P2 未定前的寫法）

- 教授的圖中偵測器在 CU；現有架構在 Near-RT RIC。KPM 由 E2 節點經 E2 送到 RIC，所以量測驗證放在 RIC 是規範上的自然位置。
- 論文中說明：「教授所指的 CU 端偵測器，於 O-RAN 中對應 Near-RT RIC 的 Detection／Trust Assessment xApp；若部署於 CU，驗證對象改為 F1 上的請求。」
- **實作限制**：ns-O-RAN 為單體 gNB，CU／DU 未實際切分、沒有真正的 F1。OAuth 只能在重放層以邏輯方式實作，論文需明寫這是**邏輯層模擬，不是協定實作**。

### 3.5 架構圖要改的地方

1. 新增 Authorization Server 與 ⓪ AuthZ Gate。
2. 被入侵的 DU 標為「學習型攻擊者」，畫出它接收判定結果的回饋箭頭。
3. Trust Assessment 內分成「L1 規則」「L2 DRL policy」「L3 規則」三塊。
4. 圖例新增「token 驗證」與「判定結果回饋（攻擊者可觀測）」兩種箭頭。

## 4. DRL 偵測端設計（L2 層）

### 4.0 不宣稱的事（〔11-07〕新增）

- 凍結的 DRL 仍是固定函數，一樣能被試探；DRL **不會**讓門檻變得不可試探。
- 線上學習會重新暴露於校準期中毒（Q6、E17）。
- 白箱假設（簡報 Assumptions 頁）本來就成立，空間參照已把不被偵測之偏差壓在約 24%（Q4）。
- 因此 DRL 可主張的增益限於：序列式升級在同一乾淨誤拒率下優於 E12 的固定持續規則；以及對學習型攻擊者的偵測延遲與可維持偏差。這兩項都要量到才寫。

### 4.1 為什麼是 DRL，而不是一般分類器

審稿人一定會問，而且正文已經有監督式分類器（E9b）當對照。理由要放在**決策是序列性的**：

1. 要不要從 low-trust 升級為 rejected，取決於前幾窗。現行規則中 S_i 的持續違反本身不升級；E12 的固定 $L_S$ 有明顯的誤拒與延遲取捨。
2. 決策的代價延後出現且會累積（steering 被誤導的成本）。
3. 攻擊者會依偵測端的決策調整行為（Q4 的 lag1 攻擊者就是這樣）。

E9b 的分類器逐窗獨立判斷，處理不了這三點。

**相關工作的區分**：Ramezanpour & Jagannath 的 i-ZTA 也以 RL 作為零信任策略引擎，輸入含 E2 KPM，但它是概念性架構、未驗證 KPM 數值本身。本研究的 DRL 只在已驗證的證據上做序列決策，而且參照不交給學習。

### 4.2 MDP 定義（建議值，寫進規格後凍結）

| 元素 | 定義 |
|---|---|
| 決策單位 | 每個 (節點 j, 秒 t)，**L1 規則未觸發時**才交給 DRL |
| state | S_i 的 $z_j(t)$ 與 peer 數；歸屬於 j 的 D1 $z_d$ 最大值與證據強度（uebound）；過去 k 秒（建議 5–10）的上述值與本 agent 的過去決策；C_i 是否處於 pending |
| action | {trusted, low-trust, rejected}；abstain 仍由 L3 規則產生 |
| reward | 正確判定 +1；漏判（攻擊下判 trusted）− α ×（該秒 steering 錯誤成本）；乾淨資料上判 rejected − β；判 low-trust 給小懲罰，避免全部判 low-trust |
| 演算法 | 離散 action，DQN 或 PPO（stable-baselines3）；固定訓練 random seed，報告多個訓練 seed |
| 切分 | 沿用 LOSO：7 個 D-30 seed 訓練、1 個測試；攻擊參數的訓練範圍與測試範圍分開報告（與 E9b 相同，必須測訓練分布外的漂移） |

### 4.3 必守原則

- DRL 不得讀取或修改 S_i 的 peer 中位數與凍結尺度 s，只讀殘差。
- 每個 DRL 結果都要與第 2 節的基線 1–4 並列。
- 必測 E9c 共模擾動；乾淨誤拒以 (節點, 秒) 為單位，與 4.9.6.3 同口徑。
- 已知缺陷：`R1_CI_PENDING` 會遮蔽同窗的 D2 否決與交叉佐證否決（4.4.0（三））。DRL 接在 L1 之後，會繼承這個遮蔽；修正規則順序需另訂規格，**不得在 DRL 規格中順手改掉**。〔11-07〕該規格為 `docs/thesis/fusion_severity_order_spec.md`（最嚴重符合規則決定），須先於 E19 完成。

### 4.4 DRL 與規則的接法：規則下限（〔11-07〕新增）

DRL 不是「L1 沒觸發才出手、然後自由決定」，而是在規則給的**下限**之內選擇（safe RL 中的 action masking／shield）：

```
L1 rejected 規則（R1_AUTHZ、R1_CI_VETO、R1_D2_VETO）觸發 → rejected，DRL 不介入
否則：floor = 規則版的判定（severity 版 fuse 之結果；含 R1_CI_PENDING → ≥ low-trust、R3 → abstain）
      DRL 只能從 {a : severity(a) ≥ severity(floor)} 中選；abstain 仍由 L3 規則產生
```

| 變體 | 下限 | 能做到 | 做不到／風險 |
|---|---|---|---|
| **V-escalate（主）** | 完整規則版判定 | 序列式升級（low-trust → rejected）、提早拒絕；偵測率不可能低於 B1 | 無法降低乾淨資料 48.7% 的 low-trust |
| V-replace（對照） | 僅 L1 + CI_PENDING + L3 | 可能降低乾淨 low-trust | 可能比規則寬鬆 → 必須在同一乾淨誤拒率下優於 B1，且通過 E9c |

理由：符合 fail-closed 原則（R3：沒有證據不等於好證據）——學習元件永遠不授予比證據規則更多的信任；規則稽核仍可追溯（`rule_id` 記下限規則，另記 `L2_DRL` 是否升級）。

## 5. 學習型攻擊者設計

| 元素 | 定義 |
|---|---|
| 控制對象 | 一個被入侵 DU 對自己 cell 上報的 delay（先做 delay；UE ID 集合與 cell 對應為第二步） |
| action | 每秒的偏移量（例如乘數 $a_t \in [0.5, 1.5]$），**限制每秒變化幅度**，逼它「慢慢改變」 |
| observation | 自己過去的上報；**偵測端對它過去的判定**（D7）；上一個已評估秒的 peer 中位數（等同 Q4 的 lag1 知識）。**不得給同秒的 peer 中位數**，那是 Q4 的 oracle，僅作上界 |
| reward | 被 steering 選中且非最佳 → +；被判 low-trust → 小懲罰；被判 rejected → 大懲罰 |
| 演算法 | 連續 action，PPO 或 SAC |

**對照點（〔11-07 修正〕不再是硬性一致性檢查）**：Q4 的 23.6% 是 oracle（β = 0.99）在「**未被 S_i 以 2c 準則偵測**」口徑下的平均偏差（4.7.8），是手寫策略，不是證明過的上界。規則版 L2 中 S_i 單獨違反只會 low-trust，要再加綁定之強 D1 才會 rejected，而 delay 攻擊者影響不了 D1——所以「**不被 rejected** 時可維持的偏差」**不受** 23.6% 限制。比較時必須用同一口徑（未被 S_i 偵測）。學習型攻擊者在同口徑下遠超過 23.6% 時，先查資訊洩漏（例如誤給了同秒 peer 中位數），但超過本身不算發現，也不算失敗。

**觀測層級**（P9）：O-full（含過去判定）與 O-outcome（只有 steering 結果）兩種都做。

**預期驗證點**：Q4 的 lag1 攻擊者是手寫策略；學習型攻擊者應能自行學到「待在 τ_S·s 附近」的策略，並在偏差與曝光之間找到類似 β ≈ 0.9 的取捨。
