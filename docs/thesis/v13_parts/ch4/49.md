## 4.9 C-ZT 四 xApp 架構、動作模式與運算開銷

### 4.9.1 定位與實作層級

本節將 C-ZT 組織為四個職責分離之 xApp：Detection、Trust Assessment、Policy Enforcement 三者將三類一致性證據經階層式融合轉為准入動作（程序 P1–P3），可用資源評估 xApp（Available-resource evaluation xApp）於每窗 P3 發布後評估准入政策下之可用資源（4.12）。此為目標部署架構；本原型以離線 trace 回放、同一行程內之邏輯模組實作四者，逐窗依序執行，未接上 live E2 與 RIC 平台。本節並量測 P1–P3 之運算開銷。E2 Termination、Subscription Management 與 shared data service 為 Near-RT RIC 平台之既有功能，非本研究之貢獻。

**實作層級之誠實聲明**：

- 四個 xApp 之邏輯皆已實作並於重放 trace 上執行。Detection、Trust Assessment、Policy Enforcement（逐窗對齊、三類證據之計算、階層式融合、依信任狀態產生准入動作）目前於同一行程（`zt_kpm_xapp.py`）內依 P1→P2→P3 依序執行，可用資源評估 xApp（`resource_eval_xapp.py`）於同一行程內、每窗 P3 發布後執行；模組間之 evidence record、trust state 與 admitted view 以行程內資料結構傳遞，未經 RIC 之 shared data service 與訊息匯流排。故本章所驗證者為各模組之邏輯及其介面內容，而非四個獨立部署之 xApp 間之通訊。
- **資料入口為 trace replay，E2 訂閱綁定尚未完成**（見 4.0.6）。程式以 `IndicationSource` 抽象層隔離資料來源，設計上擬以 `E2SubscriptionSource` 替換 `TraceReplaySource` 接上 live RIC；此替換未實作、未測試，且 OAI 之檢查顯示真實 E2 之欄位語意與本文 trace 不同（4.0.6），驗證邏輯是否須改動尚未知。
- Policy Enforcement 將 policy-admitted KPM 與 execution record 寫入共享資料層（DB）；合作消費端（RC xApp）與可用資源評估 xApp 皆自 DB 讀取。可用資源評估 xApp 於**每窗 P3 發布後即執行**（`resource_eval_xapp.py`），與 P1–P3 於同一回放迴圈中逐窗執行，而非事後之離線統計。於本原型中，DB 與 Resource Termination 為行程內之抽象層，尚未接上 RIC 之 shared data service。
- 攻擊情境下對合作消費端之保護效果，以注入後之 trace 經同一管線重放評估（4.12），未涉及 runtime 控制與閉迴路。
- 運算開銷量測反映驗證層之計算成本，**不含 E2SM-KPM 解碼與 SCTP 傳輸延遲**。

### 4.9.2 模組定義與程序

![C-ZT 架構圖](【待填：簡報 v1.2 第 28 頁之架構圖連結——P1 Detection、P2 Trust Assessment、P3 Policy Enforcement、RC xApp、DB、Resource Termination、Available-resource evaluation xApp、E2 Termination、Subscription Management】)

| xApp | 職責 | 輸入 | 輸出 |
|---|---|---|---|
| **① Detection xApp** | 將各 E2 節點（含 LTE 錨點）之上報對齊至 1 秒窗；計算 C_i、S_i、H_i-D1、H_i-D2；記錄每項證據之適用對象（場域／cell／UE）與可得性 | E2SM-KPM 上報（REPORT style，granularity period = 1 s；此為設計，原型之輸入為 trace replay）；已知 UE 母體；凍結基線 | evidence record |
| **② Trust Assessment xApp** | 套用 4.4.0 之階層式規則、交叉佐證之綁定檢查與持續窗條件 | evidence record | 逐 (節點, 窗) 之信任狀態、觸發規則代碼與佐證證據 |
| **③ Policy Enforcement xApp** | 依設定之准入政策將信任狀態轉為 allow／restrict／exclude／defer，並將 policy-admitted KPM 寫入共享資料層（DB） | 信任狀態；准入政策設定 | policy-admitted KPM、註記與 execution record（寫入 DB） |
| **④ Available-resource evaluation xApp** | 與 ①–③ 於同一回放迴圈中逐窗執行；每窗於 P3 發布後，經 Resource Termination 自 DB 讀取准入結果與各 cell 之 PRB 用量，計算可用資源指標。**不做驗證、不改變信任狀態** | DB 中之 policy-admitted KPM 與 execution record；PRB 用量（`RRU.PrbUsedDl`） | 逐窗之准入輸入可用率、$\rho_{\text{PRB}}$、PRB 能見度損失 $V_{\text{PRB}}$ |

**程序**：

| 程序 | 內容 |
|---|---|
| 初始化 | 載入已登記之節點身分、已知 UE 母體（N_known）、凍結基線（S_i 之全域尺度 $s$、H_i-D1 之停留基線）與政策設定（τ_S、τ_H、L_C、MIN_PEER、准入政策） |
| **P1** 證據偵測 | 對齊上報；計算一致性證據及其適用對象與可得性 |
| **P2** 信任評估 | 套用融合規則與狀態轉移條件，產出信任註記 |
| **P3** 政策執行 | 套用准入政策，發布 policy-admitted KPM 並記錄執行結果 |
| 逐窗執行（同一回放迴圈） | Available-resource evaluation xApp：每窗於 P3 發布後，自 DB 讀取准入結果與 PRB 用量，回報准入輸入可用率與 PRB 能見度損失（4.12） |

**evidence record 之欄位**：C_i 之 `n_total` 與嫌疑 cell；S_i 之 $z$ 值與 peer 數；D2 之瞬移 IMSI、來源／目的 cell 與是否有對應之換手事件；D1 之 $z_d$ 值、對應 UE 及其歸屬節點（4.9.6.5）。每筆信任註記含決策、觸發規則代碼與上述證據欄位；證據隨決策一併發布，使消費端與稽核者可追溯判定依據。

**execution record 之欄位**：逐窗記錄 allow／restrict／exclude／defer 之節點、准入之節點（admitted）、defer 之 fallback 設定、`out_of_scope`（LTE 錨點）、`unannotated`（應受判定之 mmWave 節點卻缺少註記者，用於發現實作缺漏），以及窗之處理狀態（`processed` 或 `n/a`）。

**execution-status 回饋**：架構圖中由 Policy Enforcement 回送 Detection 之 execution status（目前生效之限制）為**提出之介面**，本研究未實作亦未評估；現行之證據計算與判定均不依賴此回饋。

### 4.9.3 動作模式：對合作消費端之准入，而非攔截

**權限邊界**：O-RAN 架構下各 xApp 獨立向 Near-RT RIC 訂閱 E2 資料，由平台之 subscription management 管理並執行授權（xApp-TR v07 §4.2；RICARCH v09.00 §6.2.2：「Managing subscriptions from xApps to E2 Nodes; Enforcing authorization of policies controlling xApp access to messages」）；C-ZT **無權阻斷其他 xApp 之訂閱或攔截 KPM 資料流**。四種可能之動作模式比較如下：

| 模式 | 機制 | 標準相容性 | 代價 | 本研究 |
|---|---|---|---|---|
| 註記型 | 發布信任狀態與證據至共享資料層 | 相容（需消費端配合） | 保護效果取決於消費端是否採用註記 | **✓**（Trust Assessment 之輸出） |
| 中介型（限合作消費端） | Policy Enforcement 發布 policy-admitted KPM，合作之消費端改讀此視圖 | 相容（需改變該消費端之資料來源） | 增加一跳延遲；Policy Enforcement 成為該消費端之單點故障與新攻擊目標；未合作之 xApp 不受保護；時間敏感 xApp 需保留直接存取路徑 | **✓ 採用**（離線評估，4.12） |
| 攔截型 | 攔在 KPM 流前，僅轉發 trusted 資料 | 非標準（O-RAN 無此角色） | 需平台層權限 | ✗ |
| 告警型 | 僅寫日誌，不介入決策 | 完全相容 | 保護力最弱 | 併入 execution record |

中介型之一例為 Alimohammadi 等人之框架：其中毒偵測 xApp 將驗證後之 KPM 存入共享資料庫，其他 xApp 改由資料庫取用，並保留超時間敏感 xApp 之直接存取路徑（IEEE OJCOMS 2026）。本研究與之同屬此類，差異在於准入之依據為 4.4.0 之信任狀態及其可追溯之證據。

**信任狀態與動作之對應**：

| 信任狀態 | 動作 | 於 policy-admitted KPM 中之處置 |
|---|---|---|
| trusted | **allow** | 原值納入，附註記 |
| low-trust | **restrict** | 依准入政策設定：`strict` 自決策輸入排除；`restrict_annotated` 附限制註記後納入；S_i 證據不可得者兩種設定皆不准入（證據可得性閘）。兩種設定之下游差異見 4.12 |
| rejected | **exclude** | 該 (節點, 窗) 之量測不納入；寫入 execution record |
| abstain | **defer** | 於任何准入政策下皆不進入 policy-admitted KPM，待後續窗重新判定。fallback 政策（例如消費端改採其他資料來源）另行定義，且**不得使該筆量測回到 admitted view**；本章評估之 fallback 為 `none`，即消費端當窗不取得該節點之輸入 |

**准入政策**：`strict` 僅准入 allow；`restrict_annotated` 准入 allow 與 restrict（restrict 附限制註記）。exclude 與 defer 於兩者下皆不准入。實作以不變式檢查之：strict 下非 allow 之准入為 0 筆，restrict_annotated 下 defer／exclude 之准入為 0 筆。

**證據可得性閘（v12.3）**：註記之 S_i 證據不可得（`si_raw` 為 unavailable，或 `R3_ABSTAIN` 為最終或同時符合之規則）者，於任何准入政策下皆不准入；判定標籤不變，execution record 另列 `evidence_gate`（`zt_kpm_xapp.py` 之 `EVIDENCE_GATE`）。外部審稿以函式反例指出：未加此閘時，`restrict_annotated` 會准入「S_i 不可得＋D1 weak／strong」而判為 low-trust 之量測（`R3_ABSTAIN` 仍列於同時符合之規則，但准入只看最終狀態）；加閘後兩種政策皆不准入，D1 normal 之 abstain 則本來即不准入。S_i 證據不可得率取決於 UE 密度（4.7.1）；D-S12 為此閘影響 `restrict_annotated` 准入之主要情境【待定】。

**LTE 錨點**：LTE 錨點之 KPM 為驗證用之輔助輸入，不在本次准入政策之作用範圍內，於 execution record 記為 `out_of_scope`。其未進入 admitted view 之原因為不在作用範圍，**不代表 rejected 或 defer**。

**作用範圍**：Policy Enforcement 僅作用於合作消費端（本研究以 RC xApp 為例）之 KPM 輸入。C-ZT 不下達 E2SM-RC control、不阻斷其他 xApp 之訂閱，亦不對 E2 節點採取任何動作。rejected 之精確語意為**該筆量測不進入 policy-admitted KPM 並留存執行紀錄**，非判定該節點為攻擊者。驗證服務與政策設定假設位於攻擊者控制之外。向管理面之通報不在本研究之架構範圍內。

### 4.9.4 唯讀信任根

Detection xApp 之基線——per-UE-index 停留分布（H_i-D1）與全域尺度 $s$（S_i）——於**啟動時由乾淨資料載入後永不線上更新**。須區分：S_i 之**尺度與門檻**固定，**中心**則每窗由同窗其他節點即時計算；後者屬同時態參照，非固定參照。

**設計理由**：若基線隨線上資料更新，攻擊者可藉緩慢注入逐步養高門檻，使後續大幅偏移仍落於「正常」範圍——此即 4.7.3 所述滑動更新參照之結構性弱點。凍結基線使此規避路徑失效，代價為需要 **clean bootstrap 假設**，並將風險移至校準期（校準期中毒，4.7.8 Q6）。4.7.7 之非穩態結果顯示，基線與判定均不宜於場域啟動暫態期間取得或投入。


### 4.9.5 運算開銷實測

**設定**：於 D-50PH 以 LOSO 重放，逐窗量測「窗聚合完成至該窗全部 (node) 決策與准入動作產出」之處理時間（計時範圍 P1–P3；另量四個 xApp 合計）。定案組態為逐節點評估（對每個同窗活躍 mmWave 節點各產出一筆註記）、uebound、嚴重度序、`strict` 准入。量測於機器無其他負載時進行，連續執行三次。

**量測環境與程序**：

| 項目 | 設定 |
|---|---|
| CPU | 【待定：量測所用之機器】 |
| 作業系統／Python／NumPy | 【待定】 |
| 計時器 | `time.perf_counter_ns` |
| 暖身 | process 層級暖身 + 每 seed 3 回合 |
| 重複量測 | 每 seed 5 回合，**逐窗取各回合中位數** |
| 垃圾回收 | 量測期間停用 |
| 檔案 I/O | trace 預先載入，不計入 |
| 每窗記錄數 | 【待定】 |

**結果**：三次執行之 mean、P95、P99、max 與 P99 佔 1 秒 KPM granularity 之比例；P1–P3 與可用資源評估 xApp 各自及合計之處理時間【待定】。P99 為「同一窗重複五回合取中位數後、跨窗之第 99 百分位」，為離線重放之計算成本基準，不是原始請求耗時之 P99，亦非 live E2 端到端之尾延遲（不含傳輸、解碼與共享資料層）。若另以 Near-RT RIC 常引用之 10 ms 控制迴圈下界作為比較，10 ms 並非本系統已證明須符合之 deadline，僅作量級對照。

**跨 seed 差異與工作量正規化**：逐 seed 之每窗受測節點數、full-consensus 判定次數、mean 與每次判定攤提時間【待定】，用以判斷跨 seed 差異是否源自活躍節點數。

**成本模型與擴展性外推**：以同機器、同程序下兩個操作點（逐節點評估與單節點評估）解聯立 $t_{\text{window}} \approx F + S \cdot n_{\text{full}}$，$F$ 為每窗固定成本（C_i 聯集比對、H_i-D1、H_i-D2、聚合；隨 UE 數成長），$S$ 為每受測節點之 S_i 共識計算與融合成本【待定】。D-50PH 與 D-S12 之 UE 數不同，可直接觀察 $F$ 隨 UE 數之變化【待定】。此為兩點解，未檢驗線性假設；中位數運算為 $O(N \log N)$，大 N 之外推偏樂觀；單機離線量測未模擬 RIC 之併發負載。

**OAuth 之請求量**：DU 與 CU／RIC 間之 token 請求次數須於同一回放中統計（約每秒一次可接受，`meeting_minutes_advisor_20261119.md` M5）【待定】。

**範圍界定**：數值**僅涵蓋驗證層之計算成本**，不含 E2SM-KPM ASN.1 解碼、SCTP 傳輸與共享資料層寫入；DB 於本原型為行程內抽象。

### 4.9.6 融合規則稽核與乾淨資料上之決策分布

> 規則定義見 4.4.0，本節報告該定義之實作稽核結果。

#### 4.9.6.1 規則稽核之儀器化

為檢驗融合實作是否與 4.4.0 一致，xApp 加入規則稽核儀器：每筆註記除決策外，另記錄**觸發規則代碼**、**各殘差之原始判定**與**證據之綁定對象**，使「決策 × 觸發規則」可直接與規則表對帳。

稽核曾發現早期實作於第二層有兩處與規則陳述不符：其一，交叉佐證收受 H_i-D1 之 warning 證據，與「rejected 須 $z_d \geq \tau_H^{\text{reject}}$」矛盾；其二，未檢查兩項證據是否指向同一節點。修正後之規則即 4.4.0 所載版本；另 `R1_CI_PENDING` 提前返回之遮蔽已改為嚴重度序（4.4.0）。

#### 4.9.6.2 證據綁定之結構性發現

D1 量測連續 mmWave 缺席，觸發 D1 之 UE 當窗不在任何 mmWave cell 上有接收，與 S_i 受測之 mmWave 節點不可能重合——此為定義使然。故**以「當窗掛載之 cell」為歸屬依據（window 政策）時，4.4.0 之 `R2_SI_D1_BOUND` 不存在合法觸發路徑**；window 政策下 `R2_SI_D1_UNBOUND` 與 `R2_SI_D1_BOUND` 之觸發數於 D-50PH 上報告以確認此點【待定】。定案之 uebound 政策改以「UE 缺席前之 serving mmWave cell」為歸屬依據（4.9.6.5）；於該政策下，D1 證據依定義歸屬於受測節點本身，故應改看 `R2_SI_D1_BOUND` 之觸發與其證據。

#### 4.9.6.3 乾淨資料上之決策分布（window 政策，E10 之對照基線）

於**未注入任何攻擊**之資料上，以 window 註記政策執行；分母為有效 (節點, 窗) 註記；無活躍 mmWave 節點之窗為 n/a。報告決策 × 觸發規則之筆數與比例【待定】。

**預期與判讀**：window 政策以「場域內任一 UE 之 D1 證據」標記該窗全部節點；UE 數越多，幾乎每一窗都至少有一個 UE 帶有 D1 證據，trusted 比例將趨近 0。D-50PH 與 D-S12 之對照即量測此現象【待定】；此為 4.9.6.5 採 uebound 之主要依據。

**誤報之分層呈現**：本研究之 low-trust 與學習式偵測器之 FPR 並非同一量——前者為「需佐證」，後者為「良性記錄被錯誤標記為攻擊」。與後者對應之量為**乾淨資料上之 rejected 比例**（第五章之「乾淨誤拒」）。惟此對應僅及語意：學習式偵測器之 FPR 以 (UE, record) 為單位，本研究以 (節點, 窗) 為單位，**二者為對應量而非等價量，不宜以數值直接相比**。其餘註記分別陳述：可直接採信（trusted）、需佐證（low-trust）、證據不可得（abstain），三者均不計為誤報；惟於 `strict` 准入下，low-trust 之量測同樣被排除於決策輸入之外，其可用性代價見 4.12。

#### 4.9.6.4 證據可用率與 abstain 決策率之區分

S_i 之**原始判定分布**（normal／violated／unavailable；不受融合順序遮蔽；逐節點評估）【待定：D-50PH、D-S12】。abstain 決策率為「證據不可得且無其他證據」之比例，受 4.4.0 之評估順序影響（同窗另有 H_i-D1 證據時，L2 先行觸發 low-trust）；證據不可得率則為 S_i 本身無法判定之比例。二者於概念上須區分。**若高密度場域之 abstain 為 0，反映的是場域之 UE 密度，不代表 fail-closed 路徑不需要**；D-S12 為此路徑之主要檢驗。

**跨腳本對帳**：逐節點評估下 S_i 有效判定數，須與 4.10.3 之 m = 1 full-consensus trial 數相同（`run_adversarial_msweep.py` 不 import `zt_kpm_xapp.py`）【待定】。兩支獨立腳本於不同計算路徑得到同一分母，可作為資料處理一致性之交叉驗證。

**檢查之性質須區分**：本章各腳本之內建檢查分為兩類。（一）**回歸一致性檢查**：以同一判定函式重算，確認版本間逐位一致——例如 RQ3 與規則回放經 `zt_kpm_xapp.py` 之判定函式重跑（4.12、4.11），以及 E9b、E9c、E13 對 E9 與 4.9.6.5 之重現。此類檢查可排除版本分歧，但**無法排除共享函式之共同錯誤**。（二）**獨立驗證**：以原始 trace 逐筆回推、人工預期或不共享判定函式之計算路徑檢驗正確性——例如上述跨腳本對帳，以及 E11／E11b／E12 對註記之獨立重算。本章引用「一致性檢查通過」時，均指第一類，除非另行註明。

#### 4.9.6.5 E10：D1 證據之節點歸屬政策——消融與定案

**政策**：

| 政策 | D1 證據之節點歸屬 |

| window（對照） | 場域內任一 UE 之 D1 證據，標記該窗全部受測節點；交叉佐證之綁定依據為該 UE 當窗掛載之 cell |
| **uebound（定案）** | D1 證據僅歸屬於觸發該證據之 UE **缺席前之 serving mmWave cell**，即該 UE 進入本次連續 mmWave 缺席前最後一次服務它之 mmWave cell（依 RRC 連線名單與換手事件）。D1 單獨成立與交叉佐證均以此為歸屬依據。該 cell 當窗無上報者，證據僅留存為 UE 層級紀錄，不影響任何節點之信任狀態 |

**乾淨資料上之 `R2_SI_D1_BOUND` rejected**：uebound 使交叉佐證具有合法觸發路徑，乾淨資料上之觸發即為誤拒。報告其筆數與比例、依 seed 與 cell 之分布、是否集中於啟動暫態、S_i 判定之 peer 數與 z 值範圍，並以「S_i 違反率 × 節點綁有 D1 證據之比例」計算獨立假設下之預期重合數作探索性對照【待定】。此對照不足以證明兩項證據統計獨立。**此類 rejected 應報為乾淨資料上之誤拒事件，不得解讀為攻擊偵測成功。** 第五章之硬約束（學習端之乾淨誤拒 ≤ 規則版 F）即以此數為上限。

**持續性政策**：本研究保留 $L_H = 1$（凍結值）。$L_H = 2$、3 對 trusted 比例、乾淨誤拒、偵測率與延遲之影響【待定】；門檻與持續窗之完整格點見 4.9.6.6。

**一致性檢查**：「有效節點註記與現行 xApp 逐筆一致」之檢查（P0、P3 差異須為 0）【待定】。

#### 4.9.6.6 E14：D1 證據之規模效應與門檻敏感度

> **揭露**：本實驗之規格（`E14_D1_sensitivity_spec.md` v1）係於前版資料之主結果產出後撰寫；於 D-50PH 上照原規格執行。第四章之主結果一律維持凍結值（τ_H = 2／3、$L_H = 1$）；**本實驗不用於選擇操作點**。

**動機**：D1 之逐 UE 誤報率預期不隨 UE 數下降，每節點之 UE 越多，節點於任一窗至少綁有一筆 D1 證據之機率越高。本實驗量化：提高 D1 門檻或持續窗，能以多少偵測延遲換回多少可用性，以及乾淨誤拒能否因此消除。D-50PH 與 D-S12 之對照直接量測規模效應。

**設計**：LOSO、uebound；格點為 (τ_H^warn, τ_H^reject) ∈ {(2, 3)★、(3, 4)、(4, 5)、(6, 7)} × $L_H$ ∈ {1★、2、3}（★ 為凍結值）。判定直接呼叫 E10 之 `run_policy`，僅覆寫門檻，不複製判定邏輯。注入與 E10 相同（超時消失，停留長度 = ⌈median + z·σ⌉），z ∈ {3, 4, 6, 8}。內建檢查五項：凍結門檻之兩組須逐位重現 E10 之 P3／P4；trusted 之單調性；註記總數一致；門檻還原。

**結果**：各格點之乾淨資料 trusted（seed 範圍）／low-trust／rejected，以及注入之偵測率與平均偵測延遲【待定】。

**解讀規則（依規格第七節預先寫定）**：凍結之 D1 門檻係於前版資料上選定，若 D-50PH 上非最佳操作點，主結果亦不因此修改；依部署規模校準 D1 門檻與持續窗、以及使交叉佐證之強度隨「節點綁有 D1 證據之基準比例」調整，列為未來工作。第五章之學習端可於 τ_H^reject ∈ [2, 4] 內調整（5.2），其與本格點之關係於第五章報告。
