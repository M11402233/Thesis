## 1. 分級與主張上限
| 級 | 要回答的問題 | 主張上限 |
|---|---|---|
| L1 語意 | OAI KPM 之時間語意（起訖點、窗口、重置、缺值、多訂閱） | 語意對照 |
| **L2a** | **2 DU＋1 UE**：E2 報告與手動 F1 換手完整跑通；成員、空集合、身分對應 | 「C_i 所需資訊可否由原版介面取得」 |
| **L2b** | L2a 通過後加入**第二個 UE**：RFsim 連線方式、`cu-ue-id` 指定換手、多 UE 之差分正確性 | 同上，加多 UE |
| L3（暫緩） | 多 cell peer 比較之 S_i | 第二實作之結果；**正負皆報告** |

- L1／L2 全部通過，也只支持**語意與資訊可取得性**，不能升格為「C_i 偵測效果已驗證」。
- L3 之「乾淨誤報與偵測效果是否與 ns-O-RAN 同方向」是**研究問題，不是驗收門檻**（見 §5）。

## 2. 原始碼已確認之實作細節（非預防性推測）
| # | 事實 | 位置 | 影響 |
|---|---|---|---|
| S-1 | 換手只支援 F1；OAI UE 不做量測回報，只能經 telnet `ci trigger_f1_ho [cu-ue-id]` **手動觸發** | `doc/handover-tutorial.md:24–28, 106` | 成員轉移只能人為排程，不是由移動產生 |
| S-2 | RFsim 換手範例中 **UE 是 server、兩個 DU 是 client**，因為 RFsim 只支援「一個 server 配多個 client」 | `handover-tutorial.md:61, 83–85` | 「2 DU＋多 UE」**沒有文件保證**；多個 UE 都當 server 時，DU 如何連線須實測（L2b） |
| S-3 | 存在多個 UE context 時，`cu-ue-id` 必須指定，否則會拒絕換手 | `handover-tutorial.md:106–108` | L2b 之換手指令必須帶 ID |
| S-4 | 符合條件之 UE 數為 0 時 `if (arr_ue_id.sz == 0) return false;`，也就是**不送出報告**，而不是送出空集合 | `ran_func_kpm.c:409` | 消費端看到「沒有報告」，可能是空 DU，也可能是傳遞中斷 |
| S-5 | PDCP 流量、RLC throughput、PRB 之前值存於 `last_…[ue_idx]`，`ue_idx` 是**當次回報清單之位置** | `ran_func_kpm_subs.c:60–61, 79–80, 135–136, 155–156, 171–172` | UE 離開或過濾結果改變時，清單位置會換人，**可能拿另一個 UE 之前值相減**。這是原始碼顯示之風險，**尚未實測發生** |
| S-6 | 前值為 agent 內之全域狀態，多個訂閱會瓜分增量 | 同上；T2 已實測 | 每節點只保留一個訂閱者，只能避開 S-6，**不能**解決 S-5 |
| S-7 | 100 ms 平均器建在 RLC 統計層（`nr_rlc_entity.c:142–145`），E2 agent 只讀取已算好之平均 | `ran_func_kpm_subs.c:106–119` | L3 不能只改 E2 agent，見 §6 |
| S-8 | E2 報告週期以實際時間計（`period_ms = 1000`），RFsim 之無線時間可慢於實際時間 | `xapp_kpm_moni.c:36` | CPU 不足時，「1 秒窗」與無線時間脫鉤，須記錄兩者 |

## 3. L2 測試案例（真值來源與通過條件）
**真值**：CU 之 RRC／F1 log、DU log、UE log、telnet 指令紀錄、流量產生器之封包計數。**真值只用於驗收，不得悄悄當成偵測器原本就能取得之資訊。**原版介面無法區分的情況，列為 L2 之**限制**，之後再決定是否增加空集合或存活狀態訊號。

| # | 情境 | 要確認之行為 | 真值 | 通過條件（此項才算「已確認」） |
|---|---|---|---|---|
| L2-1 | 有 UE、無流量 | 成員仍列出；延遲無樣本如何呈現 | UE 之 RRC 連線狀態 | 每窗皆列出該 UE；延遲之「無樣本」與「0」是否可區分**照實記錄**（L1-T1 已見回報 0.00，預期不可區分 → 限制） |
| L2-2 | 最後一個 UE 換出 | 來源 DU 如何表示空集合 | CU 換手完成時刻 | 記錄來源 DU 之報告序列；依 S-4 預期「不送報告」→ 判定消費端能否與 L2-4 區分 |
| L2-3 | UE 存在但不符 slice 條件 | 是否與空 DU 呈現相同結果 | UE 之 S-NSSAI | 照實記錄；與 L2-2 相同即為限制 |
| L2-4 | 中斷報告傳遞（斷 E2／停 RIC 轉送） | 消費端能否辨識「資料未知」 | 中斷之開始與結束時刻 | 照實記錄；若與 L2-2／L2-3 無法區分 → 限制（C_i 之 fail-closed 必須把三者都當未知） |
| L2-5 | UE 換入目標 DU | 身分能否跨 DU 對應；過渡期間之報告 | CU 之 `cu-ue-id`、F1 log | 每次換手之前後兩份報告，`amf_ue_ngap_id`／`ran_ue_id` 對應關係逐筆列出；記錄過渡窗（兩邊都有／都沒有） |
| L2-6（L2b） | 第二個 UE 加入、離開、換手 | S-5 清單位置差分是否錯配 | 各 UE 流量產生器之 bytes | 兩 UE **流量刻意不同**（例如 1:4），逐窗比對 KPM 增量與真值；任何一窗錯配即判定 S-5 已發生 |

**L2b 前置**：先實測第二個 UE 之 RFsim 連線方式（S-2）；連不上即記錄為限制，不改拓樸硬湊。

未驗證 L2-6 之前，**不得**把 OAI 之流量／throughput／PRB 增量當成正確的負載真值。

## 5. L3（暫緩；若啟動之驗收方式）
先驗收以下五項，全部通過後，**無論 OAI 上之偵測效果與 ns-O-RAN 相同、不同或較差，皆為有效之第二實作結果**，一律報告：
1. 資料完整性（每窗每節點之報告存在或缺報有記錄）。
2. 身分對應（L2-5 之方法）。
3. 時間對齊（S-8：無線時間 vs 報告時間）。
4. 樣本有效性（延遲樣本數 > 0 之窗；無樣本之處理照語意規格）。
5. 攻擊注入正確性（注入值與報告值逐筆核對）。
